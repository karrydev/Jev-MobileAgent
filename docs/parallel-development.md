# 并行开发协作约定

适用范围：按[开发路线](development-roadmap.md)执行本地任务。任务文件在 [`.scratch/mobile-agent-v1/`](../.scratch/mobile-agent-v1/index.md)，由集成负责人统一调度；具体进度以各任务文件为准。旧 mobile-agent-development 仅作历史规划参考，不再领取。

## 1. 任务状态

每张任务保留 setup 技能约定的 `Status:`，使用默认五种 triage 状态。另用以下执行字段表达是否真正可以领取以及是否完成，避免把“规格已够 Agent 执行”误当作“前置验收已通过”。

| 字段 | 含义 |
| --- | --- |
| `Status` | `ready-for-agent` 表示规格充分；`ready-for-human` 表示存在用户必须完成的操作；其余沿用 triage 约定 |
| `Execution` | `pending`、`in-progress`、`done`；只有证据和合入检查完成后才是 done |
| `Blocked by` | 任务编号列表，编号仅用于机器解析；正文链接始终使用任务名称 |
| `Owner` / `Branch` | 当前负责人和工作分支；`unassigned` 表示未领取 |
| `Gate` | 此任务需要关闭的验收门槛；详细要求写在正文 |

可领取任务必须同时满足：`Status: ready-for-agent`、`Execution: pending`、未分配负责人、所有 `Blocked by` 已在集成分支上为 `Execution: done`。13/14 的历史人工准备已完成；21 的凭据已提供，转为 Agent 探针任务；26 是手机内闭环开发，不再是服务器资源请求。仅遇到模型账号/系统权限的实际缺口时请求用户。没有凭据或设备不能据此将真正依赖它的任务算作完成。

规格不充分时改为 `needs-info` 并记录缺少的决策。实施完成但尚未合入或验收时保持 `in-progress`，在 Comments 中说明剩余项。这里是实施任务，不使用 wayfinder 的 claimed/resolved 状态。

当前顺序与共享所有权：21/26 可并行；26 合入后可准备 22/27，但 App 运行入口、模型请求、任务持久化不能被两名实现者同时改写。按文件范围分配唯一所有者，必要时串行合入；不要为了并行新增重复运行框架。

## 2. 领取与分支

1. 集成负责人从最新 `origin/main` 检查依赖与 Owner，再串行登记 `Owner`、`Branch`、`Execution: in-progress` 并提交任务台账。领取只有在这一提交被协调确认后才生效。
2. 每个开发者或 Agent 使用独立 Git worktree 与分支，从已合入的契约版本开始；不能让多个工作者共享同一有未提交文件的工作目录。
3. 每张任务明确允许编辑范围。共享契约、根构建配置、锁文件、路线和总台账由指定负责人维护，其他工作者提出变更请求；不能同时修改公共基础后各自假定对方会适配。
4. 一张任务一个当前负责人。任务可以再拆分，但应先在台账中建立子任务与依赖，再增加并行工作者。

本地 Markdown 没有跨工作副本的原子锁，因此采用单个集成负责人串行领取。各 worktree 不能凭自己的旧台账独立领取同一任务；失去协调时先暂停领取并同步状态。

## 3. 接口先行与 Mock 边界

任务 01 先通过一个模拟任务闭环产出最小契约、正反样例、版本策略和端到端交互。后续行为切片逐步扩展契约，统一由协调者合入。当前由 App 内各模块消费共同的观察、动作和核验语义，Python 参考实现/评测通过样例对照；不要求产品继续兼容设备桥网络接口。

Mock 用来解除模块开发对真实 API、设备或服务的阻塞。每次交付必须列明：Mock 覆盖了什么、真实依赖还差什么、由哪张任务验收。生产代码不得静默切换为 Mock；真实能力缺失时返回明确不可用或等待条件。

破坏性接口变更由契约负责人先确定影响和迁移次序，更新样例，再通知依赖者；消费者不能各自发明兼容分支后继续漂移。

## 4. 合入次序

- 模块检查通过后提交变更说明、验证命令和证据摘要。实现者交付自己的分支和任务结果，集成负责人处理合入；并行工作者不同时推送主分支。
- 按任务依赖顺序合入；确需提前合入的未启用模块必须保持已有路径行为，并明确待验收项。合入不等于阶段放行。
- 目录裁剪、基线修复和功能策略各自独立提交。契约升级先于消费者适配；不得把一个工作分支临时当作其他所有人的长期基线。
- 在最终集成 SHA 上运行受影响检查和阶段必需验证，回写提交 SHA、命令、证据、限制，再把任务标为 done。
- 真机任务使用单一设备预约；改变模型、App、环境或提示词后，明确哪些已有对照失效并重跑对应检查。

## 5. 每次交接必须带上的内容

```text
任务名称与任务文件：
已合入的前置任务/契约版本：
负责人、分支、起点 SHA：
本次修改范围：
用户可见结果：
验证命令、环境与最终 SHA：
证据摘要/本地证据位置（不含凭据或私人内容）：
仍未验证的项目及依赖：
下一位接手者的具体下一步：
```

Agent 开始时读取自己的任务、前置证据和相关 ADR，不必加载全部研究材料。结构查询使用 CodeGraph；有关判断的原始研究由任务内的链接按需读取。

## 6. 暂停与失败

如果实现发现已有路线与事实冲突，记录可复现证据并标记受影响门槛，不修改成功标准使任务“通过”。先完成不依赖该结论的工作，再让负责人决定修复、回退或重新讨论产品边界。

任务停止或负责人退出时，提交已有工作和交接记录，由集成负责人解除领取。运行异常时按[手动恢复决策](adr/0002-single-device-and-explicit-resume.md)处理；不能为了测试方便省略真实用户暂停与恢复语义。
